# Linux Terminal Mechanics: File Descriptors, Pipes, and Signals

Every backend developer regularly uses command-line pipelines like `cat log.txt | grep ERROR | wc -l`. But what actually occurs beneath the shell when this command executes?

Understanding the Linux abstraction layer—file descriptors, kernel pipes, and POSIX signals—demystifies process communication and helps us architect more reliable backend services.

---

## 1. File Descriptors: Everything is a Stream of Bytes

In Unix, every open resource is represented by an integer known as a **File Descriptor (FD)**. Each process maintains its own file descriptor table managed by the kernel.

Standard conventions assign the first three descriptors:
- `0`: Standard Input (`stdin`)
- `1`: Standard Output (`stdout`)
- `2`: Standard Error (`stderr`)

When a process executes `read(0, buf, count)` or `write(1, buf, count)`, it does not know whether the source is a pseudo-terminal (`/dev/pts/*`), a regular file on an ext4 partition, or an anonymous inter-process pipe.

---

## 2. Kernel Pipes and Buffer Rings

When the shell encounters the vertical bar `|`, it calls the `pipe()` system call.

```c
int fds[2];
pipe(fds);
// fds[0] -> Read End of Pipe
// fds[1] -> Write End of Pipe
```

In the Linux kernel, a pipe is a memory-backed circular ring buffer (typically 64 KB since Linux 2.6.11). 

```text
[ Process A ] ---> stdout (fd 1) 
                         |
                 (dup2 to fds[1])
                         v
             [ Kernel 64KB Ring Buffer ]
                         |
                 (dup2 to fds[0])
                         v
[ Process B ] <--- stdin (fd 0)
```

### Flow Control and Backpressure:
- If the pipe buffer is full, the writing process is blocked by the kernel until space becomes available.
- If the pipe buffer is empty, the reading process blocks until bytes are written.
- When all write descriptors are closed, reads on the pipe return `0` (EOF).
- If a process attempts to write to a pipe with no readers, the kernel sends the `SIGPIPE` signal.

## 3. POSIX Signals and Process Lifecycle

Signals are asynchronous notifications sent by the kernel to a process to notify it of an event.

Common signals every systems programmer should master:
- `SIGINT` (`2`): Interrupt generated by `Ctrl+C`. Can be caught and handled cleanly.
- `SIGTERM` (`15`): Polite termination request. Modern daemon systems (systemd, Docker, Kubernetes) send `SIGTERM`, wait for a grace period, then proceed to `SIGKILL`.
- `SIGKILL` (`9`): Unconditional termination. Cannot be caught, blocked, or ignored.
- `SIGHUP` (`1`): Sent when the controlling terminal disconnects, or used by daemons to reload configuration files without restarting.

### Graceful Signal Handling in Python:

```python
import signal
import sys
import time

shutdown_requested = False

def handle_sigterm(signum, frame):
    global shutdown_requested
    print(f"\n[Telemetry] Caught signal {signum}. Initiating graceful shutdown...")
    shutdown_requested = True

signal.signal(signal.SIGINT, handle_sigterm)
signal.signal(signal.SIGTERM, handle_sigterm)

print("[Daemon] Running telemetry loop. Press Ctrl+C to terminate.")
while not shutdown_requested:
    # Process tasks...
    time.sleep(0.5)

print("[Daemon] Cleaned up socket buffers and state. Process exiting cleanly.")
sys.exit(0)
```

## 4. Summary: The Power of the Unix Philosophy

By keeping processes small and interconnected through simple byte streams and standardized file descriptors, Unix created an enduring paradigm for composable, observable, and modular systems software.
